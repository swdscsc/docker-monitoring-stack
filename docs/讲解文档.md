# docker-monitoring-stack 讲解文档

## 一、这套东西解决什么问题

前面三个项目是「点」：巡检脚本看一次快照，日志分析翻一次文件，备份恢复管一个库。
这套监控栈是「面」：**持续采集、长期存储、主动告警、可视化**。

具体解决三件事：

1. **看得见**：所有机器的 CPU/内存/磁盘在一个 Grafana 看板上，不用一台台登
2. **早知道**：指标异常自动告警，不用等人反馈「网站打不开了」
3. **能回溯**：出事后能翻看「昨天 14:00 内存是多少」，而不是只有当下的数字

面试时把这条链路说清楚：
> 单机脚本解决不了规模化问题，机器一多就必须有集中式的监控系统。
> Prometheus 这套栈是目前云原生环境的事实标准。

## 二、核心概念（必须理解，不然讲不了）

### 1）Pull vs Push

Prometheus 是**拉模型**：它主动去各目标的 `/metrics` 接口抓数据。

对比 Push 模型（如 InfluxDB + Telegraf、Zabbix agent 主动上报）：

| | Pull（Prometheus） | Push（传统 agent） |
| --- | --- | --- |
| 被监控端 | 只需暴露 HTTP 接口 | 需要知道监控服务器地址 |
| 新增目标 | 改一条配置 / 服务自动发现 | 每台机器配 agent |
| 目标是否存活 | 天然可知（拉不到就是挂了） | 要靠心跳判断 |

**「拉不到就是挂了」** 这一点很妙，所以 `up == 0` 就能直接做宕机告警——
这也是我规则里 `NodeDown` 的实现原理。

### 2）四种指标类型

面试常问，记住这四个：

- **Counter（计数器）**：只增不减，如 `node_cpu_seconds_total`（CPU 累计使用时间）
  用的时候必须套 `rate()`：`rate(node_cpu_seconds_total[5m])` 得到每秒速率
- **Gauge（仪表盘）**：可增可减，如 `node_memory_MemAvailable_bytes`（当前可用内存）
- **Histogram（直方图）**：分桶统计，用于计算 P95/P99 响应时间
- **Summary**：类似 Histogram，在客户端算分位数

**最容易答错的点**：直接用 Counter 的原始值没意义（它是累计值，一直涨）。
必须套 `rate()` / `irate()` 转成速率。

### 3）PromQL 两个关键函数

```promql
# rate：5 分钟窗口内的平均每秒速率（平滑，适合告警）
rate(node_cpu_seconds_total{mode="idle"}[5m])

# predict_linear：线性回归预测，预测 4 小时后磁盘剩余
predict_linear(node_filesystem_free_bytes[1h], 4 * 3600) < 0
```

`predict_linear` 是我认为这套规则里最值得讲的一条。
别的规则都是「已经坏了才报」，它是**用过去 1 小时的增长速度，推算出 4 小时后会写满**——
把「事后告警」变成了「事前预警」。运维的价值就体现在这里。

## 三、代码走读

### docker-compose.yml

```yaml
node-exporter:
  volumes:
    - /proc:/host/proc:ro      # 只读挂载宿主机 /proc
    - /sys:/host/sys:ro
    - /:/rootfs:ro,rslave
```

**为什么要挂宿主机的 /proc？**
node-exporter 跑在容器里，默认看到的是**容器自己**的资源，不是宿主机的。
要监控宿主机，必须把宿主机的 `/proc`、`/sys` 挂进去，并告诉它去哪读：

```yaml
command:
  - '--path.procfs=/host/proc'
```

这是初学者最容易踩的坑：**装完 node-exporter 发现监控的是容器而不是机器**。

`prometheus_data:/prometheus` 用命名数据卷而非直接挂目录，
避免宿主机目录权限问题（Prometheus 容器默认以非 root 用户运行）。

### alert_rules.yml

```yaml
- alert: HighCPUUsage
  expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
  for: 5m
```

拆解这个表达式：

1. `node_cpu_seconds_total{mode="idle"}` —— 筛出空闲模式的 CPU 累计时间
2. `rate(...[5m])` —— 5 分钟内的每秒速率（0~1，多核时按核累加）
3. `avg by(instance)` —— 按机器求平均
4. `* 100` 再 `100 - ...` —— 空闲率转成使用率
5. `> 80` 且 `for: 5m` —— 连续 5 分钟超 80% 才告警

**为什么用 `[5m]` 而不是 `[10s]`？**
窗口越短越敏感，但越容易误报。5 分钟能过滤掉大部分瞬时抖动，
配合 `for: 5m`，实际是「5 分钟平均持续 5 分钟超标」才算数。

### alertmanager.yml

```yaml
route:
  group_by: ['alertname', 'instance']
  group_wait: 30s
  repeat_interval: 3h

inhibit_rules:
  - source_matchers: [alertname = "NodeDown"]
    target_matchers: [severity = "warning"]
    equal: ['instance']
```

**抑制规则**这一条最能体现运维思维：
一台机器宕机，会连带触发「CPU 高」「内存高」「磁盘告警」等一堆告警。
但根本原因只有一个——**机器挂了**。
抑制规则让其他告警闭嘴，只报「宕机」这一条，避免告警风暴淹没真正的原因。

## 四、面试问答

**Q：Prometheus 和 Zabbix 有什么区别？**
> 主要在数据模型和适用场景。
> Zabbix 是传统监控，Push 模型，擅长服务器和网络设备的固定指标监控，有完整的 UI 和告警。
> Prometheus 是 Pull 模型 + 多维标签数据模型，**天然适配云原生和动态环境**
> （K8s 里 Pod 随时创建销毁，靠服务发现自动纳入监控）。
> 现在 K8s 环境下基本都用 Prometheus。

**Q：监控数据存多久？为什么？**
> 默认配了 15 天。监控数据价值随时间快速衰减，排查问题一般看最近几天；
> 本地磁盘也有限。
> 要看更长期的趋势，应该用 Thanos 或 Cortex 做远程存储和降采样——
> 原始数据存 15 天，降采样后的聚合数据存一年。

**Q：告警太多怎么办？（告警疲劳）**
> 四个手段，我这套配置里都用了：
> ① `for` 时长过滤瞬时抖动；
> ② `group_by` 合并同类告警；
> ③ `repeat_interval` 控制重发频率；
> ④ `inhibit_rules` 抑制派生告警。
> 另外还要定期做告警治理——**没有处置手册的告警就应该删掉**，否则就是在训练大家忽略告警。

**Q：node-exporter 监控到的是容器还是宿主机？**
> 默认监控容器自身。要监控宿主机必须把 `/proc`、``/sys`、`/` 挂载进容器，
> 并用 `--path.procfs=/host/proc` 指定路径。这是我配置里必须注意的地方。

**Q：如果要监控自己的业务接口（比如订单成功率）怎么做？**
> 两件事：
> ① 在业务代码里暴露 `/metrics` 接口，用 Prometheus 客户端库（Python 用 `prometheus_client`）
>    定义业务指标，比如 `order_total{status="success"}`；
> ② 在 `prometheus.yml` 里加一条 `scrape_configs` 指向业务服务。
> 这就是所谓的「埋点」——把业务指标也纳入同一套监控体系。

**Q：这套还有什么不足？**
> ① 单机部署，Prometheus 挂了监控就没了，生产应该做双副本 + Thanos；
> ② 告警没配真实接收器（webhook 是空的），告警发不出去；
> ③ 没有监控业务指标，只监控了基础设施；
> ④ 没加 blackbox_exporter，不知道外部用户访问是否正常。

## 五、动手改（挑一个）

1. **接真实告警**：在 `alertmanager.yml` 填一个钉钉/企业微信机器人 webhook，然后 `kill` 掉 node-exporter 看是否收到告警
2. **加业务埋点**：用 Python `prometheus_client` 暴露一个自定义指标，加进 `scrape_configs`
3. **加 blackbox_exporter**：监控某个 URL 是否可以访问、响应多久
4. **做一个 Grafana 看板**：CPU/内存/磁盘三个面板，导出 JSON 存进仓库（配置即代码）
